## Goal
Plans declare their predecessors in a machine-readable `depends:` key line. The iterate-run binary resolves them into a per-project graph. A plan whose predecessor has not landed is `waiting` and is never admitted, whether it would start or resume. A parked plan holds every plan behind it. Independent plans run in any order. The graph is visible in the terminal (`iterate-run plan graph`, text and Mermaid) and on the dashboard's Graph tab. Every registered project's existing plans are retrofitted with `depends:` lines: izcrOS, kingtut, filemaster, symmail, symude and the rest. The conductor can therefore never repeat the 2026-10-21 izcrOS cascade, where caiman → dace → … → jabiru launched one after another as each predecessor parked.

## Constraints
- Decision: the graph gates every admission, start and resume alike. A queued, unblocked, or executing plan with no live owner waits while a predecessor is unfinished. A plan with a live run is never interrupted. A typed `/iterate <name>` is the human override. This resolves AMBIGUOUS case dag-adm-7 as "hold it". Resuming izcrOS's seven parked dependents would only park them again.
- Decision: `waiting` and `held` are computed by the binary at read time and are never written into a plan file, so they cannot go stale.
- Decision: edges are project-local. A dependency on another project's work stays a mailbox `## Blocks` concern.
- Decision: adding, editing or retrofitting `depends:` keeps `status: queued`. Staging approves the work, and the graph orders it.
- Decision: the retrofit adds key lines only. Existing plans keep every Step, including kingtut's "Stage the next milestone" steps, which remain harmless because the graph holds whatever they stage. Staging more plans so the graph can order them is the user's act. The retrofit prints the commands and never runs them.
- Decision: one assignment per project remains (`docs/conductor.md`, "One assignment runs per project"). Within a project the graph makes ready plans run in any order. Ready plans in different projects already run concurrently under subscription concurrency. Running two plans of one project at once needs per-plan worktrees and is not this plan.
- Decision: the dependency graph is `iterate-run plan graph`. `iterate-run graph` remains the timeline alias, so no existing invocation changes meaning.
- Decision: the park-streak breaker (brainstorm option 1) and the cause of izcrOS's six `owned assignment interrupted` parks are not this plan.
- Decision: a landing archives as `<ts>-<name>-landed-rolled-to-<new>.md`. Earlier landings archived as `-done` still satisfy their edges.
- Parity: plan-state contract (`conductor.Plan`, the queue JSON, `iterate-run status`) — consumers: conductor evaluate and `Queue`, nightly tick, `iterate-run status`, `iterate-run conductor` queue output, queue API and dashboard, `/ic`, `/it`; expansion is executor work, never a gate.
